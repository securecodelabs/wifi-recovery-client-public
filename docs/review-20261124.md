# Three code-review rounds — 2026-11-24

Reviewed public v0.1.0 source `d32cbb38e447344bb51b3dafd68ee5c18d7f2797`. Fixes are committed locally as `6d08a1620e3686c2cdeb9937ae900927fea25a5f`. This review does not push changes, create tags or modify the published release.

## Round 1: job identity and lifecycle

Reviewed request routing, UUID resolution, submission, mutations, polling, terminal outcomes, and their relationship to the API's queue/stop/resume contract.

The generic decoder validated a job only if an `id` field existed, and commands did not compare the returned UUID with the requested UUID. Consequently, status/stop/resume could report success for another job, watch could use that job's terminal state, and submission could succeed without returning any job. Two new regressions reproduced exit 0 where exit 1 was required.

Job endpoints now require the typed job response. Status, watch, stop and resume additionally compare the UUID with the requested job. Invalid replies are rejected before output. The existing command, pagination, idempotent submission and export tests continued to pass. After this round, eight Windows tests and the configured Clippy checks passed; the companion API's four real CPU-engine lifecycle cases also passed.

## Round 2: input boundaries and HTTP failures

The CLI accepted runtimes longer than the engine's actual maximum of 86400 seconds, and accepted input up to 64 MiB despite the API's maximum of 8 MiB. Runtime parsing now accepts 0-86400 seconds, including `24h`; zero remains unlimited. Submission requires a regular file of 1 byte to 8 MiB and rejects oversized input before connecting. The API independently enforces its runtime limit and configurable upload limit.

Non-JSON error responses previously hid HTTP failures behind a JSON decoding error. A regression reproduced this with HTTP 502 and an ordinary text body. Error handling now retains the HTTP status and available message, limits displayed message length, and continues to escape terminal controls. Empty HTTP errors and malformed JSON on a successful response are tested separately.

The boundary tests, real HTTP regressions and all-target Clippy passed. A nesting-lint failure in the new test harness was resolved by extracting the server helper; no lint suppression or increased threshold was used.

## Round 3: failure handling and packaged executables

Two additional regressions reproduced exit 101 panics: `info` indexing a numeric resource response, and command output encountering a closed stdout pipe. Resource responses now use a typed envelope and check contract v1 before presentation or polling. Output, including embedded licenses, uses fallible writes and returns normal error exits. Tests cover both failures, unsupported resource contracts, Linux Ctrl+C, human-readable output and terminal-control escaping.

Result validation now rejects zero or more than 10000 total records, matching the API's contract, and tests unverified results. Release/CI review also found that ordinary HTTP tests selected Cargo's test binary rather than the final packaged executable. The harness now accepts `WIFI_TEST_CLIENT`; CI and manual releases run the HTTP suite against the actual built/copied executable. Version/help exit statuses are explicitly checked. Workflow triggers were preserved.
